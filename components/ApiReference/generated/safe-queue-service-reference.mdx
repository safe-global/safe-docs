# Safe Queue Service API Reference

The Safe Queue Service API Reference is a collection of endpoints to propose, confirm and list Safe multisig transactions, messages and delegates on every supported chain.

<Grid my={8} />

## Multisig transactions

<Grid my={6} />

### Create Multisig Transaction

<Grid container justifyContent='space-between'>
  <Grid item xs={12} md={5.6}>

Propose a new transaction for a Safe multisig. The first signature determines
the proposer and can come from a Safe owner, an authorized delegate or an
owner of a Safe that owns this Safe.

**Who Can Propose?**

1. **Safe Owner**: Any owner can propose with their signature
2. **Delegate**: An authorized delegate can propose on behalf of an owner
3. **Nested Safe Owner**: An EOA that owns a Safe owning this Safe

**Proposal Scenarios**

**Owner Proposal (Standard)**
- First owner becomes the proposer
- All the signatures are stored as confirmations

**Delegate Proposal**
- First signature is from a delegate (not an owner)
- Delegate must be pre-authorized for this Safe and chain
- The delegating owner becomes the proposer
- Delegate signature is NOT stored as confirmation (only owners can confirm)
- **Important**: When using a delegate, only provide the delegate's signature.
  Do not include owner signatures - they must be added separately via
  the confirmations endpoint

**Nested Safe Owner Proposal**
- For Safes whose owners are other Safes, where no owner can sign yet: the
  EIP-1271 signature or `approveHash` of an owner Safe can only be built once
  its own owners have signed, and they have nothing to sign until the proposal exists
- First signature is a plain EOA signature (`EOA` or `ETH_SIGN`) from an
  owner of an owner Safe. The ownership chain is verified on-chain
- The **owner Safe** becomes the proposer, since the signer is not an owner
  of this Safe; the signing EOA is reported in `proposedBy`, with
  `proposedVia` set to `NESTED_OWNER`
- The signature only authenticates the proposal and is NOT stored as a
  confirmation, so provide exactly one signature
- Confirmations then come from the owner Safes, either through the
  confirmations endpoint with an EIP-1271 signature, or on-chain by
  executing `approveHash`, which reaches the service through the indexer

**Nested Transaction**
- An owner Safe acts on a transaction of the Safe it owns by executing
  `approveHash(safeTxHash)` on it, or `execTransaction(...)` to approve and
  run it at once. `nestedTransaction` proposes that transaction together
  with the call acting on it, so its owners sign once
- This transaction must be a zero-value CALL to the nested Safe whose `data`
  is either call, signed by an owner of this Safe, and this Safe must own
  the nested Safe. It is stored as a regular owner proposal with its
  confirmations
- `approveHash` names the nested hash. `execTransaction` spells out the
  transaction instead: its arguments plus the `nonce` declared in
  `nestedTransaction` must produce the nested hash. The `signatures`
  argument is not inspected, and it must already cover the threshold of the
  nested Safe, so this call serves the last step of the collection
- `nestedTransaction` takes no `safe`, `chainId` or `signatures`: the Safe
  is `to`, the chain is `chainId`, and the calldata authenticates it. It is
  stored like a nested owner proposal: this Safe as `proposer`, the signer
  in `proposedBy`, no confirmations
- Both are stored together or not at all. When the nested transaction
  already exists, only the proposal is stored
- It rides on the first submission of the proposal only. Once that one is
  stored, sending it again with a `nestedTransaction` returns 409 for the
  duplicate hash and stores nothing

**Transaction Hash**

The transaction hash (`safeTxHash`) is computed using EIP-712 and includes
all transaction parameters. This hash is what owners sign to confirm execution.

**Signatures Format**

Signatures must be valid Safe signatures:
- **EOA signature**: Standard ECDSA signature (65 bytes)
- **Contract signature**: EIP-1271 compliant contract signature
- **Approved hash**: Pre-approved hash signature

Multiple signatures can be provided for owner proposals to collect confirmations
in a single request.

### List Multisig Transactions

<Grid container justifyContent='space-between'>
  <Grid item xs={12} md={5.6}>

List multisig transactions across one or several Safes.

The transactions of every Safe are merged into one list, and `offset` and
`limit` paginate that list. Each `safes` value may include colon-separated
chain IDs to restrict the results for that Safe, for example
`0xABC...:1:137`. Without chain IDs, every chain of that Safe is returned.

### Delete Multisig Transaction

<Grid container justifyContent='space-between'>
  <Grid item xs={12} md={5.6}>

Delete a pending multisig transaction proposal.

Remove a queued (not yet executed) multisig transaction. Only the original
proposer, the delegate or the nested Safe owner that proposed it can delete
the transaction.

**Authorization**

- **Proposer**: Can always delete their own transaction
- **Delegate**: Can delete if they proposed it and remain authorized for the proposer
- **Nested Safe Owner**: Can delete if they proposed it and still own the Safe
  recorded as proposer

**Signature Requirements**

Requires an EIP-712 signature from an EOA (Externally Owned Account) to prevent
replay attacks. Supported signature types: EOA (ECDSA) and ETH_SIGN.

### Create Multisig Signatures

<Grid container justifyContent='space-between'>
  <Grid item xs={12} md={5.6}>

Add owner confirmation signatures to an existing transaction proposal.

After a transaction is proposed, other Safe owners can confirm it by
submitting their signatures. Once enough signatures are collected to
meet the Safe's threshold, the transaction can be executed on-chain.

**Who Can Confirm?**

Only Safe **owners** can submit confirmation signatures. Delegates cannot
confirm transactions - they can only propose them.

An executed transaction takes no more confirmations: the request is
rejected with 422.

**Multiple Signatures**

You can submit multiple owner signatures in a single request to collect
confirmations efficiently. All signatures must:
- Be from different owners
- Not duplicate existing confirmations
- Be valid signatures of the transaction hash

**Signature Types**

Supported signature types:
- **EOA signatures**: ECDSA signatures from externally owned accounts
- **Contract signatures**: EIP-1271 compliant contract signatures
- **Approved hashes**: Pre-approved hash signatures
- **Eth Sign**: Legacy Ethereum signed message format

**Execution Threshold**

The response holds the confirmations added by this request. Get the
transaction to check whether its confirmations reach the threshold of the
Safe.

**Note**: Execution happens on-chain through the Safe contract, not through
this API.

## Delegates

### Create Delegate

<Grid container justifyContent='space-between'>
  <Grid item xs={12} md={5.6}>

Create a new delegate authorization.

Delegates allow a Safe owner to authorize another address to propose transactions
on their behalf. This is useful for granting limited proposal rights without
giving full ownership access.

**How Delegation Works**

1. A Safe **owner** (delegator) authorizes a **delegate** address
2. The delegate can propose transactions to the Safe
3. The transaction appears as proposed by the delegator (owner)
4. The delegate cannot sign transaction confirmations - only owners can
5. Delegation scope is controlled by `chainId` and `safe`:
   - Omit `chainId` (or set to `null`) → valid on **all chains**
   - Omit `safe` (or set to `null`) → valid for **all Safes**

**Required Signature**

The delegator must sign an EIP-712 typed message containing:
- `delegateAddress`: Address being authorized
- `totp`: Time-based one-time password (current TOTP value)
- `action`: The string `"add"`

The domain encodes the scope: `chainId = 0` means all chains,
`safe = 0x000...000` (zero address) means all Safes.

**TOTP Calculation**

TOTP (Time-based One-Time Password) is calculated using 1-hour intervals:

```
totp = floor((current_unix_timestamp - 0) / 3600)
```

**Parameters:**
- `current_unix_timestamp`: Current time in seconds since Unix epoch
- Time step: 3600 seconds (1 hour)
- T0 (epoch): 0 (Unix epoch start)

**Example calculation:**

Unix timestamp: 1704067200 (2024-01-01 00:00:00 UTC)
```
totp = floor(1704067200 / 3600) = 473352
```

**Tolerance window:** The service accepts both the current TOTP value and the
previous interval's value to handle clock drift between client and server.

**EIP-712 Typed Data Structure**

The delegator must sign the following EIP-712 typed data:

```json
{
  "types": {
    "EIP712Domain": [
      { "name": "name", "type": "string" },
      { "name": "version", "type": "string" },

      { "name": "safe", "type": "address" }
    ],
    "Delegate": [
      { "name": "delegateAddress", "type": "address" },
      { "name": "totp", "type": "uint256" },
      { "name": "action", "type": "string" }
    ]
  },
  "primaryType": "Delegate",
  "domain": {
    "name": "Safe Queue Service",
    "version": "1.0",

  },
  "message": {
    "delegateAddress": "0x1234567890123456789012345678901234567890",
    "totp": 473352,
    "action": "add"
  }
}
```

Replace the values with:
- `domain.chainId`: The chain ID to scope to, or **`0`** for all chains
  (maps from `null`/omitted `chainId` in the request body)
- `domain.safe`: The Safe address to scope to, or **`0x000...000`** (zero address)
  for all Safes (maps from `null`/omitted `safe` in the request body)
- `message.delegateAddress`: The address you want to authorize
- `message.totp`: Current TOTP value calculated using the formula above
- `message.action`: Must be `"add"` for this endpoint

### Delete Delegates

<Grid container justifyContent='space-between'>
  <Grid item xs={12} md={5.6}>

Delete delegate authorization(s).

Revoke delegate permissions by deleting the authorization. Like creation,
deletion requires a valid signature from the delegator (Safe owner).

**Deletion Scope**

- **Single delegate**: Specify the exact delegate address and chainId/safe
- **All delegates for a chain**: Use `0x0000000000000000000000000000000000000000`
  as delegate address, specify chainId
- **All delegates across all chains**: Use `0x0000000000000000000000000000000000000000`
  as delegate and omit chainId (or set to null)
- **All delegates for a Safe**: Specify safe address, omit delegate filter

**Required Signature**

The delegator must sign an EIP-712 typed message:
- `delegateAddress`: Address to revoke (or ADDRESS_ZERO for all)
- `totp`: Current TOTP value (calculated same as creation)
- `action`: The string `"delete"`

The domain's `chainId` and `safe` specify the scope to delete from.

This prevents unauthorized deletion of delegate permissions.

      { "name": "safe", "type": "address" }

### List Delegates

<Grid container justifyContent='space-between'>

List delegate authorizations for a known address.
