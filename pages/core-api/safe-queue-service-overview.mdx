# Safe Queue Service overview

Safe Queue Service is a REST API that stores the off-chain data of Safe accounts: multisig transaction proposals and their signatures, off-chain messages, and delegates. One service covers all supported chains. It replaces the off-chain queue endpoints of the [Safe Transaction Service](./transaction-service-overview.mdx).

## What it is

Owners use the Safe Queue Service to propose a transaction, collect the signatures of the other owners, and share signed messages. The service doesn't execute transactions. Execution happens on-chain through the Safe contract.

- The base URL is `https://api.safe.global/queue`.
- All endpoints live under `/api/v1`. For example, `https://api.safe.global/queue/api/v1/multisig-transactions`.
- Paths have no trailing slash.
- The chain is never part of the path. See [Chain handling](#chain-handling).

## Authentication

Send an API key with every request, in the `Authorization` header as a bearer token. To get a key, see [How to use API keys](./how-to-use-api-keys.mdx).

```bash
curl "https://api.safe.global/queue/api/v1/safes/0x670b24610dF99B1685AeAc0Dfd5307b92e0c54fE/multisig-transactions?chainId=1" \
  -H "Authorization: Bearer YOUR_API_KEY"
```

Requests without an API key work, but their rate limits are much lower.

### Signatures

The API key identifies your app. The signatures in the request decide who can write:

| Action | Who can sign |
| --- | --- |
| Propose a transaction | A Safe owner, a delegate of an owner, or an owner of a Safe that owns this Safe |
| Confirm a transaction or a message | Safe owners |
| Propose a message | A Safe owner, or an owner of a Safe that owns this Safe. Delegates can't propose messages. |
| Delete a pending transaction | The owner, delegate or owner of an owner Safe that proposed it |
| Add, edit or delete a delegate | The delegator |

When a delegate proposes a transaction, send the delegate's signature alone. Owners add their confirmations afterward.

Delegate changes and transaction deletions use [EIP-712](https://eips.ethereum.org/EIPS/eip-712) typed data:

- The domain name is `Safe Queue Service` and the version is `1.0`.
- The message contains a time-based one-time password (TOTP): the Unix time in seconds divided by 3600, rounded down. It changes every hour.
- The service accepts the TOTP of the current hour and of the previous hour.

Delegate signatures made for the Safe Transaction Service aren't valid in the Safe Queue Service. The delegate typed data adds a `safe` field to the domain and an `action` field to the message, with the value `add`, `edit` or `delete`. The domain `chainId` is `0` for a delegate that's valid on all chains, and `safe` is the zero address for a delegate that's valid for all Safes.

## Chain handling

The chain is never part of the path. Each endpoint takes it in a different way. The paths in this table are relative to `/api/v1`.

| Endpoint | Chain |
| --- | --- |
| `POST /multisig-transactions` | `chainId` is required in the body. |
| `POST /safes/{safe}/messages` | `chainId` is required in the body. |
| `GET /safes/{safe}/multisig-transactions`, `GET /safes/{safe}/messages` | `chainId` is an optional query filter. Without it, the list covers all chains. |
| `GET /multisig-transactions` | Each `safes` value has the format `address[:chainId...]`, for example `0xABC...:1:137`. Repeat `safes` for each Safe, up to 100 values. A Safe without chain IDs returns results from all its chains. |
| `GET /multisig-transactions/queue` | Same `safes` format, but every Safe needs at least one chain ID. Without one, the request fails with 422. |
| `GET /multisig-transactions/{safe_tx_hash}`, `GET /multisig-transactions/batch`, `GET /messages/{message_hash}` | No chain. The hash identifies the transaction or message. |
| `GET /delegates` | `chainId` is an optional filter. It only narrows a query by `safe`, `delegator` or `delegate` and can't be used on its own. |

The supported chains come from the Safe Config Service. No endpoint lists them. Write requests and `/multisig-transactions/queue` requests return 503 when the service can't get the Safe information from the chain.

## Migrate from the Safe Transaction Service

The Safe Transaction Service runs one instance per chain, under `https://api.safe.global/tx-service/{chain}`. The Safe Queue Service has a single base URL for all chains. The following table maps the replaced endpoints:

| Safe Transaction Service | Safe Queue Service |
| --- | --- |
| `GET /api/v2/delegates/` | `GET /api/v1/delegates` |
| `POST /api/v2/delegates/` | `POST /api/v1/delegates` |
| `DELETE /api/v2/delegates/{delegate_address}/` | `DELETE /api/v1/delegates`, with the delegate in the JSON body |
| `GET /api/v2/safes/{address}/multisig-transactions/` | `GET /api/v1/safes/{safe}/multisig-transactions` |
| `POST /api/v2/safes/{address}/multisig-transactions/` | `POST /api/v1/multisig-transactions`, with `safe` and `chainId` in the body |
| `GET /api/v2/multisig-transactions/{safe_tx_hash}/` | `GET /api/v1/multisig-transactions/{safe_tx_hash}` |
| `DELETE /api/v2/multisig-transactions/{safe_tx_hash}/` | `DELETE /api/v1/multisig-transactions/{safe_tx_hash}` |
| `GET /api/v1/multisig-transactions/{safe_tx_hash}/confirmations/` | No equivalent. The confirmations are part of the transaction. |
| `POST /api/v1/multisig-transactions/{safe_tx_hash}/confirmations/` | `POST /api/v1/multisig-transactions/{safe_tx_hash}/signatures` |
| `GET /api/v1/safes/{address}/messages/` | `GET /api/v1/safes/{safe}/messages` |
| `POST /api/v1/safes/{address}/messages/` | `POST /api/v1/safes/{safe}/messages` |
| `GET /api/v1/messages/{message_hash}/` | `GET /api/v1/messages/{message_hash}` |
| `POST /api/v1/messages/{message_hash}/signatures/` | `POST /api/v1/messages/{message_hash}/signatures` |

### Requests

- A transaction proposal sends its signatures in `signatures`, an array of 1 through 50 signatures. It has no `contractTransactionHash` and no `sender` field.
- The service computes the `safeTxHash` itself and returns the full transaction with status 201.
- Confirmations go to `POST .../signatures` as an array in `signatures`. You can send the signatures of several owners in one request.
- Both `DELETE` endpoints take a JSON body with the signature.
- Delegates have no expiry date.

### Responses

In a transaction, `chainId`, `nonce`, `value`, `safeTxGas`, `baseGas` and `gasPrice` are strings. These fields change name:

| Safe Transaction Service | Safe Queue Service |
| --- | --- |
| `transactionHash` | `txHash` |
| `isSuccessful` | `failed`, with the opposite meaning |
| `submissionDate` | `created` and `modified` |

The transaction has no `dataDecoded`, `isExecuted`, `executionDate`, `blockNumber`, `confirmationsRequired` or `trusted` field. To filter by execution state, use the `executed` query parameter of the list endpoints.

New transaction fields:

- `proposedVia`: how the proposal was signed, one of `OWNER`, `DELEGATE`, `NESTED_OWNER` or `UNKNOWN`.
- `proposedBy`: the address that signed the proposal, when it differs from `proposer`.
- `originName` and `originUrl`: the name and URL of the app that sent the proposal.
- `notes`: free text sent with the proposal.
- `executor`: the account that sent the execution transaction, such as a relayer or a bundler.

Messages add `preparedSignatureEip1271` and have no `safeAppId`.

To decode the `data` of a transaction, use the [Safe Decoder Service](./safe-decoder-service-overview.mdx).

### New endpoints

- `PATCH /api/v1/delegates` updates the label of a delegate.
- `GET /api/v1/multisig-transactions` lists the transactions of several Safes on several chains in one request.
- `GET /api/v1/multisig-transactions/queue` lists the pending transactions that can still be executed.
- `GET /api/v1/multisig-transactions/batch` gets up to 100 transactions by their `safeTxHash`.
- A transaction proposal can carry a `nestedTransaction`: a transaction of a Safe that this Safe owns, proposed together with the call that approves or executes it.

### Errors and pagination

- Validation errors return 422. The Safe Transaction Service returns 400.
- Duplicates return 409, for example a transaction or message hash that already exists.
- Lists take `limit` and `offset`. `limit` defaults to 50 and accepts up to 100.

## What stays in the Safe Transaction Service

The Safe Transaction Service keeps serving the data it indexes from the chain: the history of all executed transactions, including incoming transfers and module transactions, balances, Safe information, ERC-4337 Safe operations and gas estimations. The Safe Queue Service only returns multisig transactions, executed or not. See the [Safe Transaction Service overview](./transaction-service-overview.mdx).
